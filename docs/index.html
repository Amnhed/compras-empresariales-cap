Arquitectura de este backend

CAP separa el modelo, el contrato OData y las reglas. Fiori no habla con SQLite.

Arquitectura Modelo CDS Servicio OData CRUD Acciones Seguridad

Las capas

Fiori o test.http → OData V4 → ComprasService → usuario mock y @restrict → before / on / after → SQLite

db/schema.cds describe qué se guarda. srv/compras-service.cds dice qué ve el cliente. CAP genera el CRUD y lo publica en /odata/v4/compras. El JavaScript solo existe donde hay una regla que CAP no puede adivinar.

Un recorrido, registrar una orden

  1. Fiori pulsa Crear. Un POST abre un borrador. Todavía no valida.
  2. El usuario escribe el folio y los artículos. Cada cambio es un PATCH del borrador.
  3. Guardar llama a draftActivate. Ahí corre before CREATE: exige artículos y asigna el estado según el monto.
  4. La respuesta JSON vuelve por OData. after READ rellena importeTotal, que no tiene columna en la base.
  5. Antes de los pasos 1 a 4, CAP identifica a alice o bob. Si el rol no alcanza, el handler no se ejecuta.

El detalle de cada capa está en las páginas de esta carpeta. La pantalla está documentada en el proyecto compras-fiori-ui/docs.
