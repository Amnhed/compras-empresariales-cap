La autenticación responde quién llama. En local es un usuario simulado de package.json, con autenticación Basic. La autorización responde qué operación sigue. Vive en @requires y @restrict. CAP aplica las dos antes del handler: si el rol no alcanza, la respuesta es 401 o 403 y el JavaScript de negocio no corre.

service ComprasService @(requires: 'authenticated-user') {
    @odata.draft.enabled
    @(restrict: [
        { grant: ['READ'], to: ['Comprador', 'Aprobador'] },
        { grant: ['CREATE', 'UPDATE', 'DELETE'], to: ['Comprador'] },
        { grant: ['aprobar', 'rechazar'], to: ['Aprobador'] }
    ])
    entity OrdenesCompra as projection on db.OrdenesCompra actions { ... };
}
  • alice / alice, rol Comprador: lee, registra, edita y borra.
  • bob / bob, rol Aprobador: lee, aprueba y rechaza.

En test.http la cabecera Authorization: Basic ... manda ese usuario. En el navegador, al pedir el OData, el propio navegador muestra el cuadro de usuario y contraseña. Esa caja no es una página de la aplicación.

Cuando este mismo servicio se despliega en BTP, los usuarios mock se quitan y entra XSUAA. Las anotaciones @restrict se quedan: cambia quién demuestra la identidad, no las reglas de comprador y aprobador.
